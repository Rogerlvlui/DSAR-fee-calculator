  <action>
Write `packages/schemas/src/condition.ts`.

Export `CONDITION_FIELDS` as a `readonly` tuple listing exactly the field names a condition may reference, carrying a `satisfies readonly (keyof ExpenseLine | keyof Matter)[]` clause. `keyof` is a compile-time construct with no zod expression, so the closed set is enumerated once and the `satisfies` clause is what closes the loop between the PRD's type-level constraint and a runtime-checkable enum: listing a name that does not exist on either type becomes a compile error.

From `ExpenseLine`: `categoryCode`, `quantity`, `unit`, `unitRate`, `claimedAmount`, `incurredByGrade`, `isThirdPartyInvoiced`, `vendorName`, `evidenceRef`. From `Matter`: `jurisdictionCode`, `controllerType`, `currency`, `requestorClass`, `isKnownDisputeOrLitigation`, `isRepeatRequestWithin12Months`.

Export `ConditionFieldSchema = z.enum(CONDITION_FIELDS)` and `ConditionSchema` as a three-arm union exactly matching PRD §6.0: a comparison arm (`op` one of `eq`, `neq`, `gt`, `gte`, `lt`, `lte`; `value` a string, number or boolean), an `in` arm (`value` an array of string or number), and a null-check arm (`op` one of `isNull`, `isNotNull`, with no `value` key at all). Use strict objects so the null-check arm rejects a stray `value`.

Record in a module note that the alternative — loosening `field` to `string` — was considered and rejected, because it defeats the "machine-evaluable only" constraint that is the whole reason the rules are data.

Author `condition.test.ts` covering every behaviour above, including the empty `in` array case and a `@ts-expect-error` fixture proving that adding a non-existent field name to `CONDITION_FIELDS` fails to compile.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authored pack JSON → engine | Every legal proposition in the product crosses this schema; whatever it admits, the engine will execute |
| pack author → runtime evaluation | `Condition` is the only author-supplied thing the engine evaluates |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-1-EVAL | Tampering | `ConditionSchema` | high | mitigate | `field` is a closed enum bounded by a compile-time `satisfies keyof` clause; `op` is a closed set; there is no expression, template or predicate arm, so nothing author-supplied is ever evaluated as code. PRD §6.0's "no expressions to eval" is enforced by the shape rather than by convention. |
| T-1-PACKDRIFT | Tampering | `RulePackSchema` | high | mitigate | Every field is transcribed from PRD §7.2 with strict objects and closed unions; `basis` is capped at 240; `verificationStatus` is required on every rule so a rule resting on unfinished homework cannot be indistinguishable from a verified one. |
| T-1-POSTURE | Elevation of Privilege | `feePosture` | high | mitigate | Modelled as a full record over `ControllerType` rather than a single value, so a pack cannot silently apply a private-organisation posture to a public agency under a regime that treats them differently. A missing controller type fails to parse. |
| T-1-FLATFEE | Tampering | `FlatFeeSchema` | medium | mitigate | The extension is optional, carries its own `basis`, `citation` and `verificationStatus`, and is documented as usable only alongside an itemised baseline. The engine-side comparison against itemised direct cost is ENGINE-16; the lawyer-side block is REVIEW-11. |
| T-1-DEFAULT | Tampering | `constraints.profitElementPermitted`, `constraints.deterrentUsePermitted` | medium | mitigate | Both are required booleans with no schema default, so a pack that omits its position fails validation rather than inheriting a permissive one. |
</threat_model>
