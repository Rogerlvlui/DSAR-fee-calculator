<objective>
Give pack-lifecycle events the stream the frozen audit event shape cannot hold them in, and give the data-protection officer a way to read the whole log.

Purpose: the requirement that every consequential act is audited spans two record shapes, because a pack activation is about a rule pack version and has no matter to hang from — and the matter identifier on the frozen event is non-nullable by deliberate Phase 3 decision. Building only the matter-scoped half would leave that requirement half-discharged with nothing marking the gap.
Output: the second writer with an in-memory implementation and direct tests, a data-protection officer demo identity, and an export function gated on that role.
</objective>

  <action>
`packages/audit/src/memory/store.ts` — add the pack-lifecycle collection and its own monotonic counter alongside the existing ones, inside the same `globalThis`-anchored object so a refresh cannot reset one without the other.

`packages/audit/src/memory/pack-lifecycle-event-writer.ts` — the in-memory implementation of the interface plan 04-01 already declared: append, list by pack and version, export all. Mirror the matter-scoped writer exactly — zero-padded monotonic identifiers so lexicographic order is write order, deep copy on every write and every read, and the frozen payload schema parsed on every append so an undeclared key is refused by name rather than stripped. A failed append throws and stores nothing; it is never best-effort.

Validate the payload against the frozen payload schema directly. Do not author a second payload schema for this stream and do not widen the frozen one — the closed five-key set is the point, and a stream with its own private key set would be a second, unpoliced audit channel, which is exactly the tampering route this requirement exists to close.

`packages/audit/src/payload-builders.ts` — add the pack-activation and pack-edited builders. A pack activation's changed field is the pack's own lifecycle status, with the before and after values; a pack edit names the edited field. Both return the frozen payload type, so a sixth key fails the type check first.

`packages/audit/src/memory/pack-lifecycle-event-writer.test.ts`, tagged `PACK-LIFECYCLE` — the cases above. The separation test is the one that matters most: it writes into both streams and asserts each export contains only its own, because the whole reason this stream exists is that the two record shapes cannot be merged without reopening a frozen field.

Write the module header to say plainly what this does and does not discharge: the writer exists and is proven, but the write path from a real pack-activation action — the administration screen, the sole-authorship confirmation, the activation gate — belongs to the pack-administration requirement assigned to Phase 3.2. Without that note, a later reader sees a working writer and concludes the activation flow is done.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cookie value → resolved identity | The only place a role is asserted in this prototype; an unrecognised value must fall back to the least-privileged identity, never the most |
| any caller → the audit export | The single call that returns every recorded act across every matter; the widest read in the system |
| matter-scoped stream ↔ pack-lifecycle stream | Two record shapes deliberately kept apart because merging them would require reopening a frozen non-nullable field |
| payload construction → frozen payload schema | Shared by both streams; a stream validating against its own private schema would be a second, unpoliced channel |
