<task type="checkpoint:decision" gate="blocking-human">
  <name>Checkpoint: how a correction after sign-off is represented, and what happens to it next</name>
  <decision>How a correction raised after sign-off is represented, and whether the newly raised assessment can be reviewed and re-signed at all under the PRD's current transition table</decision>
  <context>
The PRD's transition table has one row left unbuilt: signed-off or closed, to superseded, on "a new assessment is raised on the same matter; the old one is retained verbatim". AC-33 states that signed-off records are immutable and that a correction is a new assessment that supersedes, never an edit.

Two facts constrain how that can be built, and together they leave a genuine gap:

1. The frozen assessment schema carries no status field of its own, and it is under an additive-only freeze. The superseded status exists on the matter, not on the assessment. So "the previous one is marked superseded" can only be expressed as the matter moving to that status.
2. The transition table gives the superseded status no outgoing row. It is terminal. So the moment a correction is raised, the matter holding both the old signed assessment and the newly raised one sits in a state from which the table permits no further move — including no route to reviewing or signing the correction.

That is not a coding preference. It is a question about how a corrected fee gets re-decided and re-signed by a named lawyer, which is the mechanism the whole product's defensibility rests on, and the PRD does not answer it. This checkpoint never auto-approves: assuming an answer here would be inventing a legal workflow.
  </context>
  <options>
    <option id="literal-transcription">
      <name>Option A — transcribe the table literally (recommended)</name>
      <pros>Invents no legal rule. The matter moves to superseded, the signed assessment is never touched, a second assessment is raised under a fresh identifier with every line undecided. The gap in the specification is made visible and flagged to you rather than papered over in code.</pros>
      <cons>The matter is terminal afterwards, so the correction is recorded but not yet reviewable or re-signable. The review path for a correction has to be resolved by a PRD amendment before any later phase can build it.</cons>
    </option>
    <option id="re-entry-row">
      <name>Option B — add a re-entry row the table does not have</name>
      <pros>The workflow is complete today: a correction can be reviewed and signed immediately, for example by permitting superseded back to computing or to legal review.</pros>
      <cons>Adds a transition the PRD's own table does not contain. That table is the artifact the "the engine applied rule X, version Y" defence is built on, and extending it without an authored amendment is the single change that most weakens the claim.</cons>
    </option>
    <option id="status-on-assessment">
      <name>Option C — move superseded onto the assessment as its own field</name>
      <pros>The matter can stay in legal review and carry the correction through the ordinary path, with no terminal dead end.</pros>
      <cons>Needs an addition to a frozen, additive-only schema and a formal freeze escalation, and it contradicts the closed seven-status set that requirement STATE-01 already marked complete.</cons>
    </option>
  </options>
  <resume-signal>Reply with the option id — `literal-transcription`, `re-entry-row` or `status-on-assessment`. If you choose the first, also say whether the open "how does a correction get re-reviewed and re-signed" question should be recorded as a blocker against a later phase or raised as a PRD amendment now.</resume-signal>

Implement whichever option the checkpoint settled on. The description below assumes Option A; if the product owner chose otherwise, follow their choice and record the divergence in the summary rather than proceeding as written.

**`apps/web/src/server/repositories/interface.ts`** — add a listing of every assessment held for a matter, in written order. Keep the method vocabulary in plain domain types, as every existing method does. State in a comment why the existing single lookup is no longer sufficient on its own: a matter can now hold more than one assessment, and a caller that needs the whole history must be able to ask for it rather than infer it.

**`apps/web/src/server/repositories/memory/assessment-repository.ts`** — implement the listing with the same deep-copy discipline as everything else in this file, and make the single lookup return the **last** assessment written for that matter rather than the first. With only one assessment per matter that is identical behaviour, which is why it is safe; with two, it is the difference between the preparer's screen showing the live correction and showing the record it superseded. Comment that reasoning where the change is made.

**`apps/web/src/server/data/assessments.ts`** — a new function raising a correction. Requires the reviewer role. Reads the matter and refuses unless it is signed off or closed. Asks the executor for the supersede event from the matter's current status and writes the destination it returns.

Then, and this is the part that must not be got wrong: the existing signed assessment is **read and never written again**. Do not update it, do not clear its dispositions, do not null its sign-off. Raise a second assessment by recomputing over the matter's current lines and giving the result a **freshly generated identifier** — the engine derives its identifier from its inputs, so if the lines have not changed the derived identifier equals the existing one, and saving under it would silently overwrite the very record this whole path exists to preserve. Generate a new identifier explicitly and comment why, in the strongest terms the file allows: this single line is the difference between a correction and the destruction of the evidence it corrects.

Record one superseded event naming the superseded assessment as the entity, with the matter's before and after status.

Do not reuse the in-place recompute module here. The two paths look similar and mean opposite things — one preserves an identity because the record is not yet final, the other creates a new identity because the old record is final and must survive. Keeping them separate, with a comment in each pointing at the other, is what stops a later reader from "removing the duplication".

**`apps/web/app/api/assessments/[id]/supersede/route.ts`** — a thin handler in the established shape, returning the conflict status when the matter is not in a state that permits a correction.

**`tests/routes/correction.test.ts`**, tagged `CORRECTION` — the cases above. The verbatim-retention test is the one that matters: snapshot the signed assessment before the correction with a deep clone, then deep-equal the stored record against that snapshot afterwards. A test asserting only that the identifier still exists would pass against a record that had been silently rewritten.

  <action>
**The closing transition.** Marking the requestor notice as sent now asks the executor for the mark-sent event and writes the destination it returns, in addition to recording the date it already records. It still sends nothing — there is no outbound message of any kind anywhere in this system, and this transition records a date and moves a status, nothing else.

This reverses an assumption recorded when the sign-off flow was built, which deferred the closing transition to the outputs phase. Reverse it deliberately and say so in the summary: this phase's own first success criterion names the closed status explicitly as something a matter must be drivable to, and no guarded executor existed when that earlier assumption was written. The outputs phase still owns the document generation; only the status change moves here.

**The consequence that is easy to miss.** The preparer-facing signed-assessment read currently refuses unless the matter is signed off. Once marking the notice sent closes the matter, that read would start refusing the preparer the figure they were just shown — a closed matter is still a signed one. Widen the read to permit both statuses and update the result screen's branch accordingly. The refusal for every earlier status stays exactly as it is: the non-negotiable is that the preparer never sees an unreviewed assessment, and a closed matter has been reviewed.

**The intake-side records.** Creating a matter, adding a cost line, replacing one and deleting one each record an event of their own kind, naming the entity and the changed values. These are not transitions, so no executor call is involved; they are the acts that produce the claim, and a log covering only the decisions would show a fee decided against lines nobody can account for. A refused edit records nothing, on the same principle every refusal in this phase follows.

Put the whole-lifecycle proof in `tests/routes/lifecycle.test.ts`, tagged `LIFECYCLE`: one test that drives a matter from creation through itemisation, submission, review, the information-request branch and back, sign-off, notice-sent and closure, asserting the status after every step and asserting at the end that the ordered sequence of recorded event types for that matter matches an expected list. That single assertion is this phase's first and fourth success criteria made observable rather than inferred.
