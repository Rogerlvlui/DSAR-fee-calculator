<objective>
Convert the remaining six hand-written status literals, give the lawyer the recompute the PRD's own table has a row for, and make every one of those acts leave a record — then remove the stand-in so it cannot be used again.

Purpose: the phase goal is that matters move only through guarded transitions and every consequential act lands in the log. Until the last literal is gone and the last transition is audited, both halves are claims rather than facts.
Output: a server whose every status write is an executor's answer, a recompute path that mutates rather than multiplies, an audit record per act, and a lint gate that keeps it that way.
</objective>

Work one function at a time and run the full suite after each one, never converting all of them and then testing. This ordering is 04-RESEARCH.md's own recommendation and exists because a regression inside a batch of six conversions is far harder to attribute than one inside a batch of one.

**`apps/web/src/server/recompute.ts`** — extract the in-place recompute mechanics into one module both callers use, so the rule that is easy to get backwards is written once. It takes the matter, its current lines and the existing assessment, re-runs the engine, and returns the recomputed assessment carrying the existing identity rather than the engine's derived one. Carry the existing comment's warning across verbatim in substance: the derived identifier is discarded deliberately and must not be "corrected" later. Have this module clear the assessment's first-opened record as part of the same operation, so no caller can perform a recompute and forget the reset — a second review pass measured from the first pass's opening silently corrupts the one signal the elapsed figure exists to produce.

**`apps/web/src/server/data/matters.ts`, `submitForAssessment`** — convert the two remaining edges. On a successful computation, ask the executor for the compute-succeeded event and write the destination it returns; on an engine failure, ask it for the compute-failed event and write that destination. Record a computed event on success and a computation-failed event on failure, the latter carrying the failure reason in the changed-value position. The rollback must still happen even when its own audit write is the thing that failed — order the rollback write before the record so a matter is never stranded mid-computation by a logging problem, and comment that ordering.

**`apps/web/src/server/data/matters.ts`, `resubmitAfterInfoRequest`** — convert both edges through the executor, delegate the mutation to the new recompute module, and record a submission event and a computed event.

**`apps/web/src/server/data/matters.ts`, a new `recomputeAgainstCurrentPack`** — the row the PRD's table has and this system has never had a caller for. Requires the reviewer role, refuses unless the matter is in legal review, asks the executor for the recompute event, delegates to the same recompute module, writes the destination, then asks for the compute-succeeded event and writes that destination. Exactly one assessment exists for the matter afterwards, under the identity it already had. It never marks anything superseded: that status exists solely for a correction made after sign-off, and this runs strictly before one.

**`apps/web/app/api/assessments/[id]/recompute/route.ts`** — a thin handler in the established shape, returning the conflict status when the matter is not in legal review.

Leave `createMatter`'s birth status alone for now; Task 3 converts it together with the lint gate that makes it necessary.

**Tests.** `tests/routes/recompute.test.ts` tagged `RECOMPUTE` for the recompute cases, with the identity assertion the important one: assert the stored identifier is unchanged and that the count of assessments held for that matter is exactly one. Same discipline as Task 1: one function at a time, full suite after each.

**The reviewer-facing read** — record the assessment as first opened, at the server's current instant, on every read. The record keeps the earliest instant, so a lawyer reloading the screen does not reset their own clock. This is the only place the origin is established.

**The single disposition** — after the existing validation and the repository write, take the elapsed reading and record a line-disposition event carrying the line identifier, the disposition the line held before and the one it holds now, and that figure. Record a sign-off event carrying the before and after status and the elapsed figure.

**The ask-for-information branch** — route the transition through the executor and record an information-requested event.

Do not remove or weaken any existing refusal in this file. Every one of them is asserted by a test written when the sign-off gate was built, and the guard's role here is to make the same answer structurally enforced, not to take over the wording.

**Delete `apps/web/src/server/state.ts`.** Every one of its callers is now converted; the type checker is the proof, because a surviving import of a deleted module cannot compile. Do not leave a re-export shim behind — a shim is how a replaced module survives for another two phases.

**`apps/web/src/server/data/matters.ts`, matter creation** — take the birth status from the constant the guard package exports rather than spelling it as a literal. A newly created matter has no transition into it, so the executor has nothing to say about it; a single named constant in the package that owns every status value is the honest expression of that, and it is what makes the lint rule below able to ban all seven values without an exception.

**`eslint.config.js`** — a bespoke syntactic rule, following the money-branding precedent exactly. Scope it to the application's server directory and its route directory. Ban an object property whose key is the matter status field and whose value is a string literal matching any of the seven statuses in the closed set. Give it its own distinct message naming what to do instead, so a developer who trips it is told to route through the executor rather than merely told no.

A literal is the thing banned, not the property: writing the destination value the executor returned is the whole point and must stay legal. Match the literal specifically, or the rule bans the one construct it exists to require.

The rule is deliberately not a dependency rule and deliberately not a change to the frozen matter type: dependency analysis inspects the import graph and cannot see an object-literal key at all, and narrowing a field on a frozen additive-only schema is a freeze escalation this phase has no mandate to take. Record that reasoning in a comment above the rule, because both alternatives look plausible to a later reader and this is the third time this codebase has had to explain which tool polices which class of rule.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| data-layer function → stored matter status | Six remaining places a status reached storage without a guard's answer behind it |
