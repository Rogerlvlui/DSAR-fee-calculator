<objective>
Finish the guard table the tracer started, and make the guard package's purity a fact CI checks rather than a convention a future contributor can quietly break.

Purpose: a state machine that enforces one row of its own table is a status field with extra steps. The defensibility claim this whole product rests on is that the engine applied a named rule — the same claim is made of every transition, so every row needs its stated preconditions actually evaluated.
Output: the complete declared transition array with one guard predicate per row, a completeness test that diffs the array against the PRD table, and two structural gates each shipping with a fixture proving it fires.

`packages/workflow/src/guards.ts` — the shared predicates, extracted so two rows that state the same precondition evaluate the same code rather than two drifting copies. At minimum: the pack-usability predicate (a pack exists, is active, and is not past its review date), the currency-match predicate (the matter's currency equals the designated currency for its jurisdiction, with a refusal naming both), the at-least-one-line predicate, the lawyer-identity predicate, and the flags-all-acknowledged predicate. Each returns the same permitted-or-refused shape a row guard returns, and each refusal names its own unmet condition specifically — a generic refusal is a dead end for whoever hits it in a browser.

`packages/workflow/src/transitions.ts` — complete the array. The PRD table has nine rows; the last of them names two origins, so the array has ten entries. Keep the entries in the PRD table's own order so the two can be diffed side by side, and keep the two supersede entries adjacent.

Row by row, the preconditions to implement:

- **Compute succeeded.** Permitted only when the assessment covers every expense line. With the frozen guard input, that is the pending-line count equalling the expense-line count with at least one line — right after computation every line is undecided, so an inequality means the engine did not return a line for every claim. Comment this derivation, because the connection between the two counts is not self-evident.
- **Compute failed.** Permitted unconditionally. The guard's job on a rollback is to let the matter out of computation, never to hold it there; the reason for the failure travels in the audit payload, not in a refusal. Say this in a comment, because an unconditional guard otherwise reads as an oversight.
- **Raise query.** A lawyer identity must be recorded. The PRD's "on at least one line" is the calling action's own content, not a state precondition the guard can see.
- **Resubmit.** The same pack-usability, currency and at-least-one-line predicates the submit row uses, deliberately re-evaluated rather than assumed from the earlier submission — the PRD's own note on this row is that the pack may have changed in the meantime, which is exactly the case a cached answer would miss.
- **Recompute.** A lawyer identity recorded and a pack available. The PRD's "confirmed first" is a screen-level confirmation, not a guard condition; note that, so nobody later tries to encode a dialog in a pure function.
- **Sign off.** Four conditions, each with its own refusal: zero lines still pending; every flag requiring acknowledgement present in the acknowledged list; a lawyer identity recorded; a pack pinned. Evaluate them in that order and refuse at the first failure.
- **Mark sent.** Permitted. The PRD records a date and nothing else here.
- **Supersede, from signed off and from closed.** A lawyer identity recorded — a correction to a signed record is a legal act and an unattributed one is indefensible.

`packages/workflow/src/transitions.test.ts`, tagged `GUARD-TABLE` — the completeness test. Assert the array's triples against an expected list transcribed by hand from the PRD table, as a single whole-array comparison so a reordering, an addition or a deletion all fail visibly. Separately assert which statuses appear as origins and which appear as none, so a future row added for a terminal status has to be a deliberate edit to this test.

`packages/workflow/src/evaluate-transition.test.ts` — extend with one block per row, each carrying the permitted case and at least one refusal per precondition that row names, asserting the refusal reason names the specific condition rather than merely that a refusal occurred.

`.dependency-cruiser.cjs` — two new rules, both anchored from the guard package, both mirroring the engine pair that already exists. The first forbids the file-system, network, DNS, child-process and worker-thread core modules. The second forbids the database client, the framework, and the sibling agent, audit, documents and rule-pack packages, plus anything under the application directory — the guard package decides, it never reaches for what it decides about, and a dependency on the audit package in particular would let a guard write an event, which is the anti-pattern the research calls out by name.

Do not add a rule attempting to police the audit package's own imports: it is a repository by nature and is I/O-shaped on purpose. Purity is the guard package's property, not this phase's blanket policy.

`package.json` — widen the depcruise script's target list to include both new packages, or the new rules are declared and never run.

`tests/fixtures/workflow-io-violation/impure.ts` — a fixture importing one forbidden core module, in the same minimal shape as the existing engine violation fixture.

`tests/toolchain/purity-gate.test.ts` — add a case per new rule, using the existing technique of widening that rule's origin scope to include the fixture directory so the rule is proven to fire without a real run ever seeing the fixture. Update the by-name rule-count assertion at the end of that file — it exists precisely so an added or renamed rule cannot slip past unnoticed, and leaving it stale would be the first time this repo's gate-integrity discipline lapsed.

`eslint.config.js` — a determinism block scoped to the guard package, mirroring the engine's: the date global, the internationalisation global, randomness and locale-formatting calls, each with its own distinct message so a test can assert which ban fired. The guard input carries no instant at all, so there is no injected clock to permit — a guard that needed the current time would be a guard reading state it was deliberately not given, and the ban makes that a lint error rather than a code review catch.

`tests/fixtures/workflow-determinism-violation.fixture.ts` and `tests/toolchain/lint-workflow-determinism.test.ts` — the fixture plus a test that lints it under a virtual path inside the guard package, exactly as the money-brand gate test does, asserting each ban's own message appears.

<assumptions>
- **The compute-succeeded guard reads completeness from the two line counts.** The frozen guard input carries no assessment-line count of its own; right after computation every line is undecided, so the pending count equalling the expense-line count is the available expression of "a line came back for every claim". Documented in the row's comment rather than resolved by widening a frozen type.
- **The compute-failed rollback is unconditional.** A guard that can refuse a rollback can strand a matter in the computing state with no way out, which is worse than any condition it might be checking for.
- **The recompute row's "confirmed first" is a screen concern, not a guard condition.** A pure function over a typed snapshot cannot observe a confirmation dialog, and encoding one there would be the first impurity in this package.
- **No purity rule is written for the audit package.** It is a repository by nature; the research recommends the repository pattern for it rather than the engine's purity pattern.
- **STATE-02 is not marked complete by this plan.** The table is complete here, but six call sites still write status literals until plan 04-04.
