Output: two frozen modules extended additively, regenerated JSON Schema artifacts, and a `FREEZE.md` amendment recording what changed and under whose authority.
</objective>

    - A `Totals` object carrying the comparison block parses, with the flat amount branded and the boolean present.
    - A comparison block whose flat amount is a non-integer, or outside the `Minor` bounds, fails to parse.
    - A comparison block missing the boolean, or carrying an undeclared extra key, fails to parse.
    - `TotalsSchema.parse` still rejects a missing `finalAmount` key and still accepts `finalAmount: null` — AC-25's shape is untouched.
  </behavior>
  <reversibility rating="costly">Additive under D-09, but Phase 3's HK pack and Phase 6's review screen both read this block, so its shape is effectively settled once those are built against it.</reversibility>
  <action>
Add `FlatFeeComparisonSchema` to `packages/schemas/src/assessment.ts` as a `z.strictObject` with exactly three fields — the pack's flat figure as a branded `Minor`, the itemised direct cost as a branded `Minor`, and a boolean recording whether the flat figure exceeds it. `strictObject` so an undeclared key is a parse error, matching the discipline used elsewhere in this package.

Attach it to `TotalsSchema` as an **optional** field, not a nullable required one. Follow the `RulePack.flatFee` precedent exactly and for the same reason: a pack with no flat fee omits the key entirely, so the JSON of every existing assessment is literally unchanged and every existing six-key totals assertion in the repository keeps passing without edit. This is also what keeps plan 02-01's tracer test and plan 02-04's golden test valid while this plan lands in the same wave.

Carry the itemised direct cost as its own stored field rather than leaving the reader to infer it from `draftBaseline`. The comparison then reads as a self-describing record of what was compared against what at computation time, which survives a later change to how `draftBaseline` is derived; a bare boolean would not.

Write a module comment above the new schema recording D-12 in the terms the decision was taken: that ENGINE-16 requires the engine to compute and report the comparison and the frozen `Totals` had no field for it; that "itemised direct cost" is **not** PRD-defined and cannot be, because `FlatFeeSchema` is itself Phase 1 invention filling a gap PRD §7.2 leaves open; and that `draftBaseline` is the defensible reading — the itemised allowable total before any lawyer disposition — grounded in `rule-pack.ts`'s own note that a flat figure cannot be shown to stay below direct cost without an itemised baseline.

No `currency` sub-field. PRD §6.0 settles that currency is a property of the jurisdiction, not of a pack or of any figure within one; the amount's currency is always `JURISDICTION_CURRENCY[pack.jurisdiction.code]`. Adding one here would reintroduce exactly the drift the D-02 gate removed from `FlatFeeSchema`.

Name the money-typed fields so the AC-07a rule applies to them, and type them as the branded schema so it passes. Never add an `eslint-disable`.

Extend `packages/schemas/src/assessment.test.ts` (red first) with the five behaviours above.
