<objective>
Add §8.1 steps 4 and 5: the cross-line checks that flag a claim's internal inconsistencies, and the aggregate cap that reduces a whole matter pro-rata when a pack carries one.

Purpose: these are the two steps where an engine is most tempted to quietly adjust a number. PRD §8.1 forbids it for the cross-line checks explicitly, and PROJECT.md settled the cap's residue policy for the same reason — an ordering rule that hits the cap exactly is an ordering rule a lawyer would have to defend. Both steps here report; neither decides.

Output: four cross-line checks and a pro-rata aggregate cap, with PRD §14's published totals still reproduced exactly.

**Scope note carried forward for the product owner.** D-13's stated reason is specific — the PRD names no threshold for implausible magnitude, and inventing one would have the engine flag on a figure no lawyer authored. Its own heading, and the Deferred Ideas list in `02-CONTEXT.md`, scope the decision to that check alone. D-13's summarising sentence, though, enumerates three checks and so also omits the third-party-evidence check, which has no threshold problem at all: it tests a boolean the PRD specifies, its flag reason code is already in the frozen schema, and ENGINE-06 names it. This plan therefore builds it and builds no implausible-magnitude check. If the product owner intended D-13 to drop the evidence check too, say so and it comes out — it is one function and one test.
</objective>

Create `packages/engine/src/cross-line-checks.ts` exporting a function that takes the evaluated lines plus their source expense lines, the matter, the pack and the claimed total, and returns the flag reasons to add per line. It computes reasons; it does not itself rewrite verdicts — task 3 applies them in one place so the verdict-and-reason invariant is enforced once.

Build exactly four checks and no fifth.

**Duplicate.** Same `categoryCode`, plus a normalised exact description match: trim, lower-case, collapse internal whitespace runs to a single space. Nothing else. Do not reach for edit distance, a similarity score, or a tunable threshold — a fixed string rule is defensible as "the engine applied this rule", and a threshold is one step from "the model decided", which is the thing this product exists not to be. Record the normalisation steps in a comment; they are the rule, and a lawyer may be told exactly what was compared. Flag every member of a duplicate group, not only the second occurrence: the engine has no basis for deciding which of two identical lines is the original.

**Materiality.** `claimedAmount * 100 >= claimedTotal * 40`, expressed as that integer cross-multiplication rather than as a division, so no float enters the money path to reach a comparison. Skip the check entirely when `claimedTotal` is zero.

**Rate sanity.** Applies where `unit` is `HOUR` and `incurredByGrade` is non-null and the pack authored a ceiling for that grade; flag where `unitRate` is strictly above it. Scope by unit and grade rather than by category code: `rateSanityCeiling` is described in PRD §7.2 as a per-grade figure, not a per-category one, so a per-grade scoping is the more literal reading and a narrower one would simply check fewer lines. The threshold is the pack's own authored number — the engine supplies none.

**Vendor evidence.** Applies to a line whose category is one of the third-party vendor categories and whose `isThirdPartyInvoiced` is false. Stand the check down where the `CategoryRule` applied to that line already carries a condition whose `field` is the same third-party-invoiced field: the rule has already tested that fact and the line is already flagged for it, and double-flagging one root cause with two codes tells the reviewing lawyer there are two problems. PRD §14's line 5 is exactly this case — it is `isThirdPartyInvoiced: false` and §14 lists two reasons for it, not three — so the golden test in task 3 is what holds this behaviour in place.

Build **no** implausible-magnitude check. D-13: the PRD names no threshold, and a flag raised on a number no lawyer authored is precisely the failure PRD §0's fourth non-negotiable exists to prevent. `rateSanityCeiling` already catches the realistic case using a pack-authored figure. Write a short comment at the bottom of the module naming D-13, saying the check is deliberately absent and that if one is wanted it belongs in the rule pack as counsel-authored data — so a later reader finds a decision rather than an oversight.

Every message comes from `packages/engine/src/messages.ts`, stays inside `FlagReasonSchema`'s 200-character cap, and describes what the engine compared rather than pronouncing on the result. These templates are engine-authored rather than pack-authored, so they are the strings plan 02-07's language test enumerates.

Write `packages/engine/src/cross-line-checks.test.ts` first, red, covering every behaviour above including each near-miss boundary.

  <action>
Create `packages/engine/src/aggregate-cap.ts` exporting a pure `applyAggregateCap(capAmount, allowedAmounts)` returning `{ allocated, residue, bound }`, plus the step function that maps it over the assessment lines.

Mechanics, per research Pattern 3 and PROJECT.md's settled policy:
  - Sum the amounts of every ALLOW and ALLOW_CAPPED line. If the sum is at or below the cap, return unchanged with `bound: false` — no reduction, no residue reported, no flag. Running the pro-rata pass anyway would be a no-op that nonetheless tells a lawyer the cap did something.
  - Otherwise each line's share is the floor of `capAmount * lineAmount / sum`. Multiply before dividing, floor once. The residue is the cap minus the sum of the allocated shares and is left unallocated. Rounding each line down and leaving the remainder matches `applyCap`'s own discipline and accepts an under-claim as the cheaper error; the two schemes that hit the cap exactly were considered and rejected because both introduce an ordering rule a lawyer would have to defend.
  - Guard the zero-sum case before the division ever executes.

Verdict handling, per D-11: a line whose amount the cap reduced keeps verdict ALLOW_CAPPED and keeps contributing its reduced amount to `draftBaseline`. It does not acquire a flag reason — the frozen `AssessmentLineSchema` refinement makes a reason on a non-FLAG line unrepresentable, and flipping the line to FLAG instead would drop a line the pack allows out of the fee entirely, changing the computed figure rather than its presentation. Both alternatives were considered and rejected at the D-11 gate. Set `appliedCap` on each reduced line to the aggregate cap, so the line records which cap moved it.

The notice that the cap bit is a **matter-level** flag using the code plan 02-03 added, with `requiresAcknowledgement: true` — a fee reduced by a cap is something a lawyer should have to acknowledge rather than scroll past. Push it onto the assessment's matter-flag array. Plan 02-06 owns that array's final composition and ordering; append here and let that plan sort.

Only a `PER_MATTER` aggregate cap is meaningful at this step. Handle a `PERCENT_OF_CLAIM` aggregate cap as a percentage of `claimedTotal` floored; a `PER_UNIT` or `PER_LINE` value in `constraints.aggregateCap` has no matter-wide meaning, so raise the typed error added in plan 02-04 rather than guessing — and note that Phase 3's pack validator should reject those two at build time.

Create `packages/engine/src/__fixtures__/aggregate-cap-pack.ts` — a small dedicated fixture with a binding cap, deliberately separate from the §14 reference fixture, whose `aggregateCap` is null and must stay null. No real pack has a non-null aggregate cap yet, so this behaviour is proven on a purpose-built fixture rather than under fixture-matching pressure.

Write `packages/engine/src/aggregate-cap.test.ts` first, red, covering all seven behaviours above. Assert `AssessmentLineSchema.parse()` on the reduced lines.
