<objective>
Build the spine of `packages/engine`: one expense line travelling the whole way through `assess()` — preconditions, per-line evaluation, totals, a schema-valid `Assessment` — plus the two supporting modules that path needs (typed precondition errors, Date-free calendar arithmetic).

Purpose: PRD §14 says to build the reference fixture first because every later formula is checked against it rather than against reasoning. This plan proves the shape of the pipeline end to end on one line before any treatment, cap, cross-line check or matter flag exists, so an architectural mistake in the `Assessment` construction surfaces after one commit rather than after six.

Output: a callable `assess()` that handles the ALLOW path correctly and refuses, with a typed error, every input PRD §8.1 step 1 says it must refuse.
</objective>

Create `packages/engine/src/totals.ts` exporting `computeTotals(assessmentLines, expenseLinesById, appliedRuleById)`. The five formulas, from research Pattern 1, derived by reproducing PRD §14's own published numbers:
  - `claimedTotal` = Σ `claimedAmount` over every expense line
  - `draftBaseline` = Σ `engineAmount` over lines whose verdict is ALLOW or ALLOW_CAPPED
  - `disallowedTotal` = Σ `claimedAmount` over DISALLOW lines **plus** Σ (`claimedAmount` − `engineAmount`) over ALLOW_CAPPED lines. The second term is not in PRD §8.1 step 6's prose; it is forced by §14's own arithmetic, where 120.00 + (33.00 − 26.40) = 126.60. Omitting it yields 120.00 and fails the golden file with a symptom that looks like a totals bug rather than a spec-reading one.
  - `flaggedTotal` = Σ `claimedAmount` over FLAG lines (their `engineAmount` is 0 — AC-11)
  - `restingOnUnverifiedRules` = Σ `engineAmount` over ALLOW/ALLOW_CAPPED lines whose applied `CategoryRule.verificationStatus` is `NEEDS_VERIFICATION` (AC-22 — a subset of `draftBaseline`, never an addition to it)
`finalAmount` is set to `null` literally and unconditionally. Do not give it a parameter, a default, or a branch that could ever assign `draftBaseline` to it (AC-25). Run each computed total through `MinorSchema.parse()` before returning: a JS number can exceed the 32-bit range these fields are bounded to without throwing, and a silently out-of-range total is a tampering surface (threat T-2-02).

Create `packages/engine/src/assess.ts` exporting `assess(input: { matter: Matter; lines: ExpenseLine[]; pack: RulePack; now: string }): Assessment`, matching PRD §8.1's signature exactly.   </behavior>
  <action>
Create `packages/engine/src/calendar-math.ts`: a pure integer day-count module with no reference to the `Date` global, no date library, and no locale API. Research Pattern 4 chose this over an ESLint-exempted module deliberately — one exempted file weakens the determinism gate to "no clock outside one file", and the arithmetic is roughly fifteen lines.

Export:
  - `parseIsoCalendarParts(value: string): { year: number; month: number; day: number }` — strict, anchored regex accepting either a bare `YYYY-MM-DD` calendar date or a `YYYY-MM-DDTHH:MM:SS(.sss)?Z` UTC datetime, taking only the calendar portion of the latter. Reject anything else by throwing; do not fall through to a permissive parse. Range-check month 1–12 and day 1–(days in that month, leap-aware).
  - `civilToDayNumber(year, month, day): number` — the standard proleptic-Gregorian days-from-civil algorithm, pure integer arithmetic.
  - `daysUntil(nowIsoDateTime: string, targetIsoDate: string): number` — `civilToDayNumber(target) − civilToDayNumber(now)`. Positive means the target is in the future, zero means today, negative means past. Both callers (the staleness precondition in task 3, the 30-day warning in plan 02-06) read this one function, so the day-boundary semantics are decided once.

Because neither string is ever handed to an environment-dependent parser, the result is invariant under `TZ` by construction — which is the property plan 02-07's timezone test exists to prove rather than assume.

Write `packages/engine/src/calendar-math.test.ts` first, red: the behaviour cases above as explicit unit tests, plus a `fast-check` property over a bounded year range (1970–2100) asserting antisymmetry and add-then-difference round-tripping. Use `fast-check` from the root install; if the import does not resolve from `packages/engine`, add `"fast-check": "4.10.0"` (the exact root-pinned version, never a range — `tests/toolchain/pins.test.ts` enforces this) to `packages/engine/package.json` devDependencies and re-run.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → `assess()` | A `Matter`/`ExpenseLine[]`/`RulePack` may have been mapped from a Postgres row without passing back through zod. The engine treats its own arguments as untrusted and re-checks the invariants a wrong fee would rest on. |
| `assess()` → `Assessment` | The engine's output becomes the record a lawyer signs. Anything wrong here is wrong in a legal work product, not merely in a UI. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2-01 | Tampering | `totals.ts` money arithmetic | high | mitigate | Integer `Minor` only; no division anywhere in this plan's code path; every total round-tripped through `MinorSchema.parse()` before it is returned. |
| T-2-02 | Tampering | `totals.ts` aggregate sums | high | mitigate | A JS number silently exceeds the 32-bit range these Postgres `Int` columns hold; `MinorSchema.parse()` on each computed total converts a silent overflow into a thrown bound error at the point of computation. |
| T-2-05 | Spoofing | `preconditions.ts` | high | mitigate | A stale, non-ACTIVE, wrong-controller-type or wrong-currency pack would produce a figure with no legal authority behind it. Six independent precondition checks at the engine's own boundary (ASVS V5), each throwing rather than degrading. |
| T-2-06 | Repudiation | `assess.ts` identity derivation | medium | mitigate | Identifiers are derived deterministically from `matter.id`, pack id/version and `now`, so the same inputs always reproduce the same assessment identity — a re-run is checkable against the audit record rather than being a fresh, unrelated object. |
| T-2-07 | Tampering | engine determinism | high | mitigate | No `Date`, `Date.now()`, `Math.random()` or `crypto` in this package; calendar comparisons are integer arithmetic over ISO strings. Statically gated by plan 02-02 and proven at runtime by plan 02-07. |
| T-2-SC | Tampering | package-manager installs | low | accept | This plan installs no new package. `02-RESEARCH.md` §Package Legitimacy Audit records that `packages/engine` adds zero runtime dependencies; the only possible `package.json` edit is promoting the already-installed, root-pinned `fast-check@4.10.0` into `packages/engine`'s devDependencies. |
