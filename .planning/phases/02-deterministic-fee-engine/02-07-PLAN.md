<objective>
Prove the four properties the engine claims but has not yet demonstrated: that its output does not move with the host's timezone, that it meets the 100ms budget, that its money stays integral across ten thousand generated inputs, and that it never pronounces on legality.

Purpose: each of these is a gate, and this phase's governing lesson is that a gate which has never been observed failing is indistinguishable from one that inspects nothing. Every test here therefore ships with a companion assertion proving the harness itself can fail — a control value that must differ under a timezone flip, a control function that must blow the performance budget.

Output: four proofs, each of which has been watched failing on purpose.
</objective>

  <action>
Create `packages/engine/src/purity.tz.test.ts`.

Use Vitest's own environment-stubbing API to set the timezone, paired with the matching un-stub call in an `afterEach`, rather than assigning to `process.env` directly — the value is then restored even when a test throws. Research verified on this machine that Node re-reads the timezone variable per computation rather than once at startup, so no subprocess spawn and no cross-environment package is needed; a single test file flips it in process.

Pick the two settings to maximise the chance of exposing a day-boundary bug: UTC, and the most extreme currently-observed positive offset. Run the same `assess()` call under each and compare the two results with a deep equality assertion. Include the staleness-boundary fixture, because the thirty-day window comparison is the only place in the engine where a day boundary could matter at all.

Then the part that makes this test worth having. Add a control assertion in the same file: compute a value through the platform's own timezone-sensitive date handling under each of the two settings and assert the two results **differ**. If that assertion ever passes trivially — because the stub is not taking effect, or because the installed Vitest version isolates environment variables differently than expected — it fails, and it fails before the invariance assertions can pass for the wrong reason. Keep this control in the test file only; it must never appear in `packages/engine/src` production source, where plan 02-02's lint rule bans it and correctly so.

The locale half of Success Criterion 2 is deliberately **not** tested here. Research verified on this machine that the language environment variable does not move Node's default locale, so a locale-flip test would pass while testing nothing — the exact Phase 1 failure mode this phase exists to stop repeating. Its enforcement is plan 02-02's static ban on the locale APIs, and the tests proving that ban fires. State this in a comment at the top of the file, with a pointer to plan 02-02, so a later reader does not "complete" the test by adding an inert locale flip.

Confirm the installed Vitest version's default isolation for the `engine` project before relying on the stub across sibling files; if environment variables are shared across a worker rather than isolated per file, add the narrowest configuration needed and record why in `vitest.config.ts`.
  </action>

Create `packages/engine/src/perf.test.ts` following research Pattern 5:
  - Build the fixture once, outside the timed region.
  - Run `assess()` a small number of times and discard the results, so the first measured run is not paying just-in-time compilation cost.
  - Take twenty measured samples, each timing a single `assess()` call with the high-resolution timer from Node's performance hooks — not the platform date API, which plan 02-02's lint rule bans in this package and which has neither the resolution nor the timezone-independence this needs.
  - Sort the samples and assert the median is under the budget. Use the median rather than the mean or the maximum: a single scheduling hiccup on a loaded machine moves the mean and dominates the maximum, and a gate that fails because another process was busy is a gate that gets deleted.

Then prove the harness can fail. Factor the sampling loop into a small local helper taking the function to measure, and add a second test that runs the identical helper over a control function containing a tight busy-loop long enough to exceed the budget, asserting that its median is **over** 100ms. The control is a local function in the test file, not a modification to `assess()` and not a temporary edit that gets removed — a proof that only existed during development is not a proof the suite retains.

Do not use the benchmark runner. It is built for tracking regression trends across runs on controlled hardware, and research found its run-to-run variance on shared hardware is a documented problem for exactly this use — a merge-blocking assertion built on it reproduces the flaky-test-gets-deleted failure mode directly.

Start at §11's literal 100ms. If it proves genuinely marginal on this machine, record the measured medians in the SUMMARY rather than quietly widening the budget; a softened acceptance criterion needs evidence and a decision, not a commit.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host environment → engine output | A timezone or locale difference between a developer machine, CI and a pilot host must not change a computed fee. The lint rule scans only the engine's own source; a dependency's internal clock read is invisible to it, so a runtime test is the actual proof. |
| engine-authored text → the legal work product | Every string the engine writes ends up in a document a lawyer signs. A word implying a legal conclusion turns a description of a rule into a pronouncement on legality. |
