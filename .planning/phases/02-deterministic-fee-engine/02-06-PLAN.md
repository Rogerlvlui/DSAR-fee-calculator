  <behavior>
    - A rule with an always arm produces a flag on every matter.
    - A rule with a condition arm produces a flag only where the condition holds against the matter; conditions referencing a line-level field are evaluated against each line and produce one flag if any line matches.
    - A rule with a line-count arm compares the number of expense lines against its value using its operator, inclusively for both `gte` and `lte`.
    - Each produced flag carries the rule's `flagId` as its id, its message verbatim, its acknowledgement requirement, and the pack-flag code.
    - A pack with no rules produces no pack flags and does not throw.
    - Two rules matching produce two flags, in the order the rules appear in the pack.
  </behavior>
  <action>
Create `packages/engine/src/matter-flags.ts` exporting `evaluatePackFlagRules(pack, matter, lines)`.

Handle all three `when` arms of `MatterFlagRuleSchema`. Discriminate structurally rather than by guessing: the always arm has an `always` key, the line-count arm has a `field` of the line-count literal, and anything else with a `field` is a `Condition`. Use an exhaustive check so an unrecognised shape throws rather than being silently skipped — a pack rule that quietly never fires is a legal warning a lawyer never sees.

Reuse `evaluateConditions` from `packages/engine/src/conditions.ts` for the condition arm. Do not write a second evaluator: the closed field vocabulary and the comparison semantics must be identical to the ones used on category rules, or a pack author writing the same predicate in two places gets two different answers.

A condition arm may reference either a matter field or a line field, because `CONDITION_FIELDS` spans both. Evaluate a matter-field condition once against the matter; evaluate a line-field condition against each line and emit the flag if any line satisfies it. State that "any line" rule in a comment — it is a decision, and the alternative (every line) would make most such rules unfirable.

Every produced flag uses the pack-flag code from `MatterFlagCodeSchema`, carries the rule's own `flagId` as the flag id, and takes `requiresAcknowledgement` from the rule rather than defaulting it — PRD §14's three informational SG flags are exactly the case where defaulting it to true would block sign-off on a flag that is not meant to block anything.

Pack-authored `message` text passes through verbatim. It is counsel's wording, and Phase 3's pack validator owns checking it against the banned-word list; the engine neither edits it nor re-validates it.

Write `packages/engine/src/matter-flags.test.ts` first, red, covering all six behaviours, and parse each produced flag through `MatterFlagSchema`.
