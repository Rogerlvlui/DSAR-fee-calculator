<decisions>
## Implementation Decisions

Decision IDs are kept at their original Phase 1 numbering so the two CONTEXT files, the plans, and the discussion log all still agree. D-01, D-02, D-03 and D-10 remain Phase 1's and are not restated here; D-07 and D-09 are restated as informational because they constrain this phase too.

### Walking-skeleton routes

- **D-04:** The skeleton is **one read per role area plus one write that audits**:
  - `/hr/matters`, `/legal/queue`, `/admin/rulepacks` each read through Prisma as `dsar_runtime`. Empty result sets are a passing outcome — the point is that the query executes under the restricted role.
  - One POST creates a `DRAFT` matter and emits a `MATTER_CREATED` audit event.

  This proves guard → Prisma → runtime role → audit write end to end over real HTTP, rather than proving the guard and the database separately. The three list surfaces are Phase 3/5/6 deliverables anyway, so part of the skeleton survives rather than being discarded. — **Reversibility:** reversible.

- **D-05:** Skeleton scope discipline holds regardless: the POST is a bare typed endpoint, **not** Phase 5's intake form. No disclosure shell, no capability statement, no status strip, no repeater, no autosave — those are DISC-01..03 and INTAKE-01..09, and belong to Phase 5. Phase 5 is expected to rewrite this POST against the real form and its validation.

### Database-level invariants

- **D-06 (second tranche):** Every DB-level invariant derivable from a frozen type lands with the freeze — audit GRANT/REVOKE, `MatterStatus` as a real Postgres enum, the `currency = JURISDICTION_CURRENCY[jurisdictionCode]` check constraint, and no cascade deletes near audit or signed-off records. Phase 1 authored these in `schema.prisma`; this phase **applies and falsifies** them against a live instance. The one-way door was already confirmed at Phase 1's D-06 checkpoint, so this tranche is rated `costly` and does not re-ask. — **Reversibility:** costly — each is a migration; loosening one later needs a new migration and an explanation of why the invariant stopped holding.

- **D-08:** The runtime must **fail fast on boot** if `SELECT current_user` returns `dsar_migrator` — the split is silently unenforced otherwise, and AC-34 would pass in principle while being false in practice. Separate env vars for the two connection strings.

### Carried constraints from Phase 1

- **D-07 [informational]:** Still holds — the `SIGNED_OFF` immutability trigger is **Phase 4's**, not this phase's. Do not write it here either.
- **D-09 [informational]:** Still holds — the freeze is additive-only. This phase applies migrations for an already-frozen model; it does not rename, retype or remove a frozen field.

### Not yet decided — needs re-planning after Phase 3.1

The repository swap — replacing Phase 3.1's in-memory implementation with a Prisma-backed one behind the same interface — is **deliberately not recorded as a decision here.** It presumes an interface that does not exist yet, so committing to it now would be guessing at Phase 3.1's output. It is carried as a forward note in `<deferred>` below, and becomes a real decision when this phase is re-planned after 3.1 ships. The three plans in this directory predate it and do not cover it.

</decisions>

<specifics>
## Specific Ideas

- **"Empty is a pass."** The three skeleton reads return empty result sets and that is a successful outcome — what is proven is that the query executes under the `dsar_runtime` role through the guard, not that there is data to show.
- **Fail fast on `current_user`.** The migrator/runtime split is silently unenforced if the app boots with the wrong connection string "because it's simpler" — hence D-08's startup assertion rather than trusting configuration.
- **AC-34 is a PRD §0 non-negotiable.** Until this phase runs, the append-only audit guarantee is unproven. No pilot deployment may follow Phase 3.1's demo while this phase is outstanding.

</specifics>
