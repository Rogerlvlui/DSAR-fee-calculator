Build the legal review screen the phase exists to demonstrate, and make every disposition a real, reasoned, server-enforced decision.

Purpose: success criterion 3 is entirely here — no headline while anything is pending, a reason demanded for every disposition, bulk accept restricted to verified supported lines, and every line showing its rule id, basis and citation without further interaction. This is the screen the presentation is about.
Output: the three-region review screen, per-verdict disposition controls, the live bulk-accept bar, and the integer tallies the sign-off panel will consume.

`apps/web/src/domain/review-tallies.ts` — two pure exports over an array of assessment lines. `computeReviewTallies(lines)` returns the counts of each disposition plus the sum of lawyer-allowed amounts. `computeFinalAmount(lines)` throws if any line is still pending, and otherwise returns the integer sum: the engine's amount for an accepted line, the lawyer's amount for a reduced or lawyer-allowed line, and zero for a struck line. Integer addition only — no division, no rounding, no floating-point intermediate anywhere, because this is the money path and the branded minor-unit type is the only representation it has. Comment the module with what it is and is not: this is the review-time arithmetic the demo needs, it lives outside `packages/engine` because the engine's frozen surface has no disposition-aware recompute, and Phase 6 owns the production version. It is pure and lives under `src/domain/` so the totals rail and the sign-off panel read the same numbers.

`apps/web/src/server/data/assessments.ts` — add `dispositionLine(actor, assessmentLineId, input)`. It requires the legal-reviewer role first, then validates in this order, refusing with a typed error at the first failure:
  - the action is one the line's verdict permits, per the per-verdict control list above;
  - the reason has at least ten non-whitespace characters and is within the frozen lawyer-reason cap;
  - where the action carries an amount, that amount parses as a branded minor-unit integer, is not negative, does not exceed the originating expense line's claimed amount, and for a reduction does not exceed the engine's own amount for that line.
Only after all of that does it write the disposition, the decided amount, the reason, the acting user and the server timestamp through the repository, and only through the repository. A refusal writes nothing at all — a partially applied disposition is worse than a rejected one, because the lawyer cannot see that it half-happened.

Every disposition requires a reason. Annex A varies the reason label by verdict ("required", "required if you change the amount", "required to allow anyway") and those labels are rendered verbatim, but the server rule is uniform, because this phase's success criterion 3 states it plainly: every disposition demands its reason. Record that reconciliation in the plan SUMMARY so a later phase does not read the varying labels as varying rules.
