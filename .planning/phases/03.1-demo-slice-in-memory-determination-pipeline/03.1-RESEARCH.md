# Phase 03.1: Demo Slice — In-Memory Determination Pipeline - Research

**Researched:** 2026-09-18
**Domain:** Next.js 16 App Router UI over an already-frozen deterministic engine/schema/rulepacks stack; in-memory persistence behind a swappable repository interface
**Confidence:** MEDIUM-HIGH (the domain layer below `apps/web` is fully built and read verbatim this session; the Next.js/testing layer is cross-checked web research; one finding below is a verified, load-bearing data discrepancy)

## Summary

This phase builds `apps/web` from nothing — no Next.js app exists anywhere in the repository yet — on top of three packages that are complete, frozen, and must not be re-opened: `packages/schemas`, `packages/engine`, `packages/rulepacks`. The engine's public surface is a single pure function, `assess({ matter, lines, pack, now }) -> Assessment`, already proven against PRD §14's reference fixture inside `packages/engine`'s own test suite. The job of this phase is wiring, not computation: HR-shaped forms that produce a `Matter` and `ExpenseLine[]`, a thin in-memory repository that holds them across requests, a call to `assess()`, a legal-review screen that renders the returned `Assessment` and collects dispositions, and a sign-off action — all under Next.js App Router route handlers that already have a **matching test project pre-wired** (`vitest.config.ts`'s `"routes"` and `"web"` projects target `tests/routes/**/*.test.ts` and `apps/web/**/*.test.tsx`, neither of which exist yet).

**The single most important finding in this research is a verified, load-bearing discrepancy between the real committed `SG-PDPA/2026.09.1.json` pack and the PRD §14 fixture this phase must reproduce.** The real pack marks `SG-PDPA.STAFF_TIME_SEARCH`'s `verificationStatus` as `NEEDS_VERIFICATION` — not `VERIFIED`, as PRD §14's own worked example and the engine's internal test fixture (`packages/engine/src/__fixtures__/reference-pack.ts`) require. Running `assess()` against the real pack exactly as committed today will *not* reproduce `restingOnUnverifiedRules: 106.40` (success criterion 2) — it will produce `266.40` (the entire `draftBaseline`), because all three allowed lines, not two, would carry `NEEDS_VERIFICATION`. A second, independent blocker: the real pack's `status` is `"DRAFT"`, and `packages/engine`'s own `checkPreconditions()` throws `PACK_NOT_ACTIVE` for any non-`"ACTIVE"` pack — so `assess()` cannot run against the file as committed at all without an explicit, documented in-memory override. Both are detailed in Common Pitfalls #1 below, with exact file/line citations and recommended resolutions.

**Primary recommendation:** Build `apps/web` as a single Next.js 16 App Router app using Route Handlers (not Server Actions) for every state-changing action, a Data Access Layer module (`server-only`, role-checked) sitting between routes and a repository interface, and an in-memory repository implementation keyed by a `globalThis`-anchored singleton so state survives across requests and Fast Refresh in dev. Fix the two pack-content issues above via a small, explicit, clearly-logged in-memory transform at the engine-invocation boundary — never by silently editing what the status strip claims the pack's real state is.

### Pattern 1: Route Handlers as the only mutation surface, DAL as the only place that checks roles

**What:** Every `route.ts` under `app/api/` is thin: parse+validate the body with a zod schema from `@dsar/schemas`, delegate to a `src/server/data/*.ts` function, translate the function's result/thrown error into an HTTP status code and JSON body, done. All authorisation and all repository access happens inside `src/server/data/*.ts`, never inside the route handler itself and never in `middleware.ts`.

**When to use:** Every state-changing action in this phase (create matter, add/edit/delete line, submit, disposition, sign off).

**Example** (adapting the pattern Next.js's official docs demonstrate for mutations — `[CITED: nextjs.org/docs/app/guides/data-security]`, fetched in full this session):
```ts
// src/server/data/matters.ts
import "server-only";
import { MatterSchema } from "@dsar/schemas/matter";
import { getCurrentUser } from "./auth.ts";
import { matterRepository } from "../repositories/memory/matter-repository.ts";

export async function createMatter(input: unknown) {
  const user = await getCurrentUser();
  if (user.role !== "HR_PREPARER") {
    throw new ForbiddenError("Only HR_PREPARER may create a matter");
  }
  const matter = MatterSchema.parse(input); // reuses the SAME frozen schema, not a re-derived shape
  return matterRepository.create(matter);
}
```
```ts
// app/api/matters/route.ts
import { NextResponse } from "next/server";
import { createMatter } from "@/server/data/matters";

export async function POST(request: Request) {
  const body = await request.json();
  try {
    const matter = await createMatter(body);
    return NextResponse.json(matter, { status: 201 });
  } catch (error) {
    if (error instanceof ForbiddenError) return NextResponse.json({ error: error.message }, { status: 403 });
    if (error instanceof ZodError) return NextResponse.json({ error: error.issues }, { status: 400 });
    throw error;
  }
}
```

### Pattern 2: Repository interface with no import from any store implementation (success criterion 4)

**What:** `src/server/repositories/interface.ts` declares `MatterRepository`/`AssessmentRepository` as plain TypeScript interfaces whose method signatures use only `@dsar/schemas` types (`Matter`, `Assessment`) — never a storage-specific row shape. `src/server/repositories/memory/*.ts` implements those interfaces. A dependency-cruiser rule (mirroring the repo's existing `.dependency-cruiser.cjs` pattern for `packages/engine`'s purity, `[VERIFIED: .dependency-cruiser.cjs:1-58]`) makes the "no import from any store implementation" claim a CI-enforced fact, not a convention:

```js
// .dependency-cruiser.cjs — additive rule alongside the existing four
{
  name: "no-store-impl-in-repository-interface",
  severity: "error",
  comment:
    "The repository interface module must be swappable for a Prisma implementation later without any screen or engine call site noticing — it must not itself depend on a concrete store (success criterion 4, Phase 03.1).",
  from: { path: "^apps/web/src/server/repositories/interface\\.ts$" },
  to: { path: "^apps/web/src/server/repositories/(memory|prisma)" },
},
```
And add `apps/web` to the existing `depcruise` script's target list (`"depcruise": "depcruise --config .dependency-cruiser.cjs packages/engine packages/schemas apps/web"`) so this new rule actually runs in CI.

**When to use:** This is the literal mechanism success criterion 4 asks for — "proven by the interface module having no import from any store implementation." A hand-written unit test asserting "the file's source text contains no `from \"./memory` string" is a weaker, gameable substitute; prefer the dependency-cruiser rule because it inspects the resolved import graph the same way the existing engine-purity rule does, and it is one more line in a config file the team already trusts.

### Pattern 3: In-memory singleton store anchored to `globalThis` (survives Fast Refresh)

**What:** Next.js's dev server uses Fast Refresh / Hot Module Replacement, which re-evaluates changed modules — a plain module-level `const store = new Map()` gets silently reset (or, worse, duplicated across webpack chunks) whenever a file changes during the demo. The well-documented workaround — the same one used for a Prisma client singleton in Next.js apps — is to anchor the singleton to `globalThis` `[CITED: web research, cross-checked across multiple sources this session — MEDIUM confidence]`:

```ts
// src/server/repositories/memory/store.ts
import type { Matter } from "@dsar/schemas/matter";
import type { Assessment } from "@dsar/schemas/assessment";

interface DemoStore {
  matters: Map<string, Matter>;
  assessments: Map<string, Assessment>;
}

declare global {
  // eslint-disable-next-line no-var
  var __dsarDemoStore: DemoStore | undefined;
}

export const demoStore: DemoStore =
  globalThis.__dsarDemoStore ??
  (globalThis.__dsarDemoStore = { matters: new Map(), assessments: new Map() });
```

**When to use:** Every place that would otherwise declare a fresh in-memory collection at module scope in `apps/web`. Without this, a presenter's demo can silently "lose" a matter mid-walkthrough after an unrelated file save triggers Fast Refresh — a bad failure mode for a stakeholder presentation.

**Pitfall this pattern does NOT solve:** in a genuine multi-worker production deployment this pattern gives each worker its own copy — but that is exactly the throwaway-persistence problem Phase 3.2 exists to replace, and is explicitly out of scope for a single-process local demo (success criterion 1 requires "no database" and implicitly a single dev-server process, matching `pnpm dev`).

### Pattern 4: Data Access Layer for role checks (fills the empty Q6 in `.claude/CLAUDE.md`)

**What:** Per Next.js's own current guidance (`nextjs.org/docs/app/guides/data-security`, version 16.3.5 — matching this repo's installed Next.js version exactly, fetched in full this session): *"For new projects, we recommend creating a dedicated Data Access Layer (DAL)... A Data Access Layer should: Only run on the server [`import 'server-only'`]. Perform authorization checks. Return safe, minimal Data Transfer Objects."* And, on why not middleware: *"middleware can't be trusted for authorization... Authorization checks should be performed in the data access layer itself."* `[CITED: nextjs.org/docs/app/guides/data-security]`

Applied to this project: a `requireRole(role: Role)` helper lives in `src/server/data/auth.ts`, imported and called at the top of every `src/server/data/*.ts` function — never relied upon via a page-level check alone, because (per the same doc) *"A page-level authentication check does not extend to the Server Actions [or, by the same logic, any other server-only function] defined within it... Always re-verify inside the action."*

**When to use:** Every function in `src/server/data/`. Since this phase has "stubbed identity" (no real SSO yet, per CLAUDE.md's Prototype framing constraint), `getCurrentUser()` can be a fixed stub resolved from the route group (`/hr/*` → a hardcoded `HR_PREPARER` `UserRef`; `/legal/*` → a hardcoded `LEGAL_REVIEWER` `UserRef`) — but the *shape* of the check (`requireRole()` called inside the DAL function, not the route handler, not middleware) should already be the real, carry-forward pattern, per this phase's scope discipline ("screens and engine wiring are production-quality").

### Pattern 5: Engine invocation with a demo-scoped pack coercion, clearly logged and clearly displayed

**What:** See Common Pitfalls #1 for the full discrepancy. The resolution pattern:

```ts
// src/server/engine-invocation.ts
import "server-only";
import { resolveRulePack } from "@dsar/rulepacks/loader";
import { assess, type AssessInput } from "@dsar/engine";
import type { RulePack } from "@dsar/schemas/rule-pack";

// DEMO-ONLY TRANSFORM — never used by a real ACTIVE-pack workflow (Phase 6+).
// The real SG-PDPA/2026.09.1.json pack is still DRAFT and NEEDS_VERIFICATION
// on every authored category (see 03.1-RESEARCH.md Pitfall #1). This function
// makes that override visible and named, rather than a silent JSON edit or a
// silent runtime patch that the status strip would then contradict.
export function coercePackForDemoEngine(loaded: ReturnType<typeof resolveRulePack>): RulePack {
  return {
    ...loaded,
    status: "ACTIVE", // checkPreconditions() requires this; the real pack is DRAFT
    constraints: loaded.constraints as RulePack["constraints"], // already all-non-null in this pack's committed JSON
  };
}
```
The UI's status strip and capability statement must continue to read the pack's *real* loaded status (`"DRAFT"`) from the untransformed `resolveRulePack()` result — never from the coerced copy — so success criterion 5 ("the demo never overstates itself") holds even while the engine itself runs against a coerced-active copy.

## Common Pitfalls

### Pitfall 1: The real SG-PDPA pack cannot reproduce PRD §14's fixture exactly, as committed today

**What goes wrong:** Success criterion 2 requires `assess()` applying "the authored SG-PDPA pack" to reproduce `restingOnUnverifiedRules: 106.40` exactly. Running the *real*, committed pack produces `266.40` instead, and additionally throws `PACK_NOT_ACTIVE` before it can compute anything at all.

**Why it happens — verified, with exact citations:**
1. `packages/rulepacks/SG-PDPA/2026.09.1.json` (`[VERIFIED: packages/rulepacks/SG-PDPA/2026.09.1.json:53-65]`) sets `SG-PDPA.STAFF_TIME_SEARCH`'s `"verificationStatus": "NEEDS_VERIFICATION"` — quoted verbatim: `"ruleId": "SG-PDPA.STAFF_TIME_SEARCH", ... "verificationStatus": "NEEDS_VERIFICATION"`. PRD §14's own table only marks line #2 (`STAFF_TIME_COLLATE`) as `"(unverified rule)"`, implying line #1 (`STAFF_TIME_SEARCH`) is verified.
2. The engine's own test fixture module says this explicitly, in its own header comment (`[VERIFIED: packages/engine/src/__fixtures__/reference-pack.ts:26-34]`, quoted verbatim): *"Research derived the first two (STAFF_TIME_SEARCH VERIFIED, STAFF_TIME_COLLATE NEEDS_VERIFICATION) by arithmetic from §14's own published restingOnUnverifiedRules figure (106.40 = 80.00 + 26.40, not 160.00 + 80.00 + 26.40 ...). §7.6 describes the REAL SG-PDPA production pack as shipping all 21 categories NEEDS_VERIFICATION initially — that is a different pack; copying that description into this fixture would make the golden test fail by exactly 160.00."*
3. `packages/rulepacks/SG-PDPA/2026.09.1.json`'s top-level `"status": "DRAFT"` (`[VERIFIED: packages/rulepacks/SG-PDPA/2026.09.1.json:8]`) means `packages/engine/src/preconditions.ts`'s `checkPreconditions()` throws `AssessPreconditionFailure` with code `PACK_NOT_ACTIVE` on the very first check (`[VERIFIED: packages/engine/src/preconditions.ts:50-55]`, quoted: `if (pack.status !== "ACTIVE") { throw new AssessPreconditionFailure({ code: "PACK_NOT_ACTIVE", ... }`) — the real pack cannot be handed to `assess()` at all without a transform.
4. The pack cannot legitimately *reach* real `ACTIVE` status either: `assertActiveReady()` (`[VERIFIED: packages/rulepacks/src/validate.ts:153-164,189-220]`) throws `MISSING_REVIEWER` (all of `authoredBy`/`reviewedBy`/`reviewedOn` are `null` in the committed file) and would separately throw `UNAUTHORED_CONTENT` for the 15 stub categories that still carry the `UNAUTHORED` token in their `verificationNote` — full authoring is explicitly deferred (D-16, per `STATE.md`) to "before Phase 6," not this phase.

**How to avoid:** Do not edit the committed pack file's `status` field to fake `"ACTIVE"` (that would make the status strip lie about a fact success criterion 5 requires to stay honest). Instead:
- **Recommended, needs a lightweight confirmation, not a stop-and-ask:** update `packages/rulepacks/SG-PDPA/2026.09.1.json`'s `SG-PDPA.STAFF_TIME_SEARCH.verificationStatus` from `"NEEDS_VERIFICATION"` to `"VERIFIED"` (a one-line JSON content edit, not a rewrite of pack authoring) — this is squarely within what `.planning/ROADMAP.md`'s own "Depends on" line for this phase already anticipates: *"enough of PACK-09 to cover the PRD §14 reference fixture."* The bulk-accept button in the mockup itself already assumes exactly this (`"Accept verified supported lines (1)"` — only works if exactly one ALLOW line, `STAFF_TIME_SEARCH`, is `VERIFIED`; `[VERIFIED: docs/dsar-fee-agent-mockup.html:961]`).
- Separately, at the engine-invocation boundary only (never in the committed JSON), construct an in-memory copy of the loaded pack with `status: "ACTIVE"` for the sole purpose of satisfying `checkPreconditions()` — see Pattern 5 above. Continue to render the pack's *real* `"DRAFT"` status in the status strip/capability statement from the untransformed load result.
- Flag both changes explicitly for product-owner confirmation before the plan locks them in — this is pack content, which is nominally counsel's domain, even though the specific value (matching PRD's own worked example) is a low-risk, already-implied correction rather than a new legal position.

**Warning signs:** `assess()` throwing `PACK_NOT_ACTIVE` the first time the demo route is wired up; `restingOnUnverifiedRules` computing to `266.40` (all of `draftBaseline`) instead of `106.40` once the status issue is fixed but the verification-status issue is not.

### Pitfall 2: Next.js dev server Fast Refresh resets module-level state

**What goes wrong:** A plain `const store = new Map()` at module scope in `apps/web` appears to work, then "loses" data the presenter just entered the moment an unrelated file is saved during the live demo.

**Why it happens:** Webpack module re-evaluation on Fast Refresh, plus webpack's chunk-splitting duplicating a naively-scoped singleton across chunks `[CITED: web research, cross-checked — MEDIUM confidence]`.

**How to avoid:** Anchor the store to `globalThis` (Pattern 3 above) — the same technique long used for a Prisma client singleton in Next.js apps.

**Warning signs:** A matter created moments ago 404s after any code change; totals reset between HR intake and legal review during rehearsal.

### Pitfall 3: `vitest.workspace.ts` is the wrong file to create — it's deprecated

**What goes wrong:** A planner instinctively creates `vitest.workspace.ts` for the new `apps/web` test project, following older tutorials.

**Why it happens:** `vitest.workspace.ts` was the mechanism before Vitest 3.2; Vitest 5 (the version this repo runs) replaced it with a `projects` array field inside the root `test` config `[CITED: web research, cross-checked — MEDIUM confidence]`.

**How to avoid:** Nothing needs creating — the root `vitest.config.ts` **already declares** the `"web"` project (jsdom, `apps/web/**/*.test.tsx`) and the `"routes"` project (node, `tests/routes/**/*.test.ts`) `[VERIFIED: vitest.config.ts:71-77,32-38]`. This phase's job is to populate matching files, not to author new Vitest config plumbing. Confirm the field name hasn't moved again in a later 5.x patch before relying on this comment (the repo's own `vitest.config.ts` header already carries this same caution, quoted: *"Confirmed against the installed vitest@5.0.0 type declarations"*).

**Warning signs:** `pnpm test` reporting the "web" or "routes" project matched zero test files even after adding `.test.tsx`/`.test.ts` files — check the glob and `environment` fields match what was actually created.

### Pitfall 4: Server Actions look safe; they are still public POST endpoints

**What goes wrong:** A developer wires a form directly to a `"use server"` action for convenience, skipping the Route Handler + DAL split.

**Why it happens:** Server Actions look like an ordinary function call from the calling component.

**How to avoid:** Already decided against in `.claude/CLAUDE.md` Q8. Reinforced by Next.js's own current docs, fetched this session: *"By default, when a Server Action is created and exported, it is reachable via a direct POST request, not just through your application's UI... you should still treat Server Actions as reachable via direct POST requests and verify authentication and authorization inside each one."* `[CITED: nextjs.org/docs/app/guides/data-security]` Use Route Handlers + DAL (Patterns 1 and 4) for every mutation in this phase.

### Pitfall 5: `next dev`'s default font loading can reach the network

**What goes wrong:** `create-next-app`-style scaffolding commonly wires `next/font/google` in the default layout, which fetches font files at build/dev-start time — contradicting "no network" (success criterion 1) even though the fetched fonts are then self-hosted/cached.

**How to avoid:** Use `next/font/local` or plain system-font CSS in `apps/web`'s root layout; do not add a Google-fonts import when scaffolding. Also set `NEXT_TELEMETRY_DISABLED=1` (or run `next telemetry disable` once) so the dev server doesn't attempt its anonymous telemetry ping — this doesn't block startup without network, but it keeps the "no network" claim literally true rather than "no network that mattered."

### Pitfall 6: the existing AC-06 DOM denylist test runs against a canary fixture, not a real form — that changes once this phase exists

**What goes wrong:** `tests/boundary/dom-denylist.test.ts` currently proves the personal-data field-name denylist against `tests/fixtures/denylist-canary.fixture.tsx` because, per `STATE.md`, "no form yet exists." Once this phase's intake form exists, that test's coverage claim becomes stale unless someone deliberately re-points or extends it at the real rendered form.

**How to avoid:** Flag this for the plan: add (or extend) a boundary test asserting the *real* HR intake form's rendered DOM contains no `name`/`id` attribute matching `PERSONAL_DATA_DENY_LIST` (`@dsar/schemas/constants`), alongside — not instead of — the existing canary fixture test.

### Pitfall 7: this phase has no real audit backbone (Phase 4 hasn't run yet)

**What goes wrong:** A plan might assume `AuditEvent` writes are available, or skip them silently in a way that looks like a design decision rather than an acknowledged gap.

**How to avoid:** State explicitly in the demo's capability statement / status strip that audit-event persistence is not yet wired (Phase 4 delivers the append-only backbone) — this phase's sign-off action can still *construct* the shape of an audit event in memory (matching `AuditEventTypeSchema`/`AuditEventType`) for realism, but must not claim a durable, append-only log exists yet. This keeps success criterion 5 ("the demo never overstates itself") honest about this specific gap too.

## Open Questions

1. **Should the repository interface + in-memory implementation live inside `apps/web` or as a new workspace package?**
   - What we know: PRD §15's suggested structure has no dedicated persistence package; `packages/rulepacks` already depends on `packages/engine` (an existing cross-package dependency direction, per Phase 3 P04's note), so a new package dependency direction isn't unprecedented.
   - What's unclear: whether Phase 3.2's Prisma swap-in will be easier if the interface already lives in its own package (importable from a future `packages/persistence` without moving code) versus inside `apps/web/src/server/`.
   - Recommendation: keep it inside `apps/web/src/server/repositories/` for this phase (simpler, no new package boundary to justify) and let Phase 3.2 decide whether to extract it — success criterion 4's actual test (dependency-cruiser rule) works identically either way.

2. **What should the demo's `now` value be?**
   - What we know: `assess()` takes `now` as an explicit input (no internal clock read); PRD §14's reference fixture uses `"2026-09-15T00:00:00Z"`; the real SG-PDPA pack's `reviewDueOn` is `"2027-03-12"`, far enough out that `STALE_PACK_WARNING` won't fire against a realistic wall-clock `now` in September 2026.
   - What's unclear: whether the presentation wants `STALE_PACK_WARNING` to visibly fire (matching PRD §14's expected matter flags list) or is fine without it (success criterion 2's explicit value list doesn't include matter flags).
   - Recommendation: use live wall-clock `now` for a more convincing "real system" demo; accept that `STALE_PACK_WARNING` won't fire (not required by success criterion 2), and note this explicitly if a stakeholder expects to see every PRD §14 matter flag reproduced.

3. **Where does the AC-23 lawyer-reason stop-list constant belong for this phase's disposition UI, given AC-23 itself is Phase 6's?**
   - What we know: PRD §13 AC-23 specifies the exact stop-list (`["ok","okay","fine","agreed","yes","no","n/a","na","noted","as above","same"]`) and that it "lives in one exported constant used by both client and server" — but no such constant exists yet in `@dsar/schemas/constants` (only `PERSONAL_DATA_DENY_LIST` and `LEGAL_CONCLUSION_BANNED_WORDS` are exported there today).
   - What's unclear: whether this phase's disposition reason field should implement real stop-list validation (getting ahead of Phase 6) or just a length check.
   - Recommendation: implement only a minimum-length check (matching the mockup's "0 / 10 characters minimum" counter, `[VERIFIED: docs/dsar-fee-agent-mockup.html:999]`) for this phase, and leave the stop-list itself to Phase 6, which owns AC-23. Adding the stop-list constant to `@dsar/schemas/constants` now would be a legitimate small addition if the planner wants full parity with the mockup, but is not required by this phase's stated success criteria.
