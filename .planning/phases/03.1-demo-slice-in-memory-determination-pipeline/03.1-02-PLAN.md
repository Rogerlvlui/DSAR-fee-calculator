  <action>
Build the intake screen as one client form composed of four presentational pieces, fed by a server-computed pack view model.

`apps/web/src/server/pack-view.ts` — `buildIntakePackView()` reads `loadDemoPack()` and returns a plain, serialisable object: the pack id and version, its real status, the fee posture per controller type, and a per-category entry carrying the category code, its label from `EXPENSE_CATEGORY_LABELS`, the pack rule's own `basis` string as the contextual hint, and the rule's verification status. The hint text comes from the pack, never from a sentence typed into a component — PRD §10.2 calls this the place HR learns the rules over time, and a hint that disagrees with the pack teaches the wrong thing. This module is server-side and imports the server guard.

`apps/web/app/(hr)/layout.tsx` — the HR route-group shell. `apps/web/app/(hr)/matters/new/page.tsx` — an async server component that resolves the actor, builds the pack view and renders the form with it as props.

`apps/web/src/ui/intake/matter-details-fields.tsx` — section 1: reference (pre-filled with a suggested value, editable), jurisdiction select, legal entity, controller type, request-received date, currency and requestor class. Currency is derived from the chosen jurisdiction through `JURISDICTION_CURRENCY` and rendered read-only with a one-line explanation that each jurisdiction has exactly one designated currency — it is not a free choice and must not be offered as one. The moment a jurisdiction is chosen, the pack's status for it is shown inline; when its posture records no express authority or prohibits a fee, render the PRD §10.2 heads-up paragraph verbatim, before section 3 becomes reachable. Telling HR before they spend twenty minutes itemising is the point.

`apps/web/src/ui/intake/attestations-panel.tsx` — section 2, locked until section 1 is valid, per §10.2's progressive-disclosure rule. Three checkboxes, each with its one-line explanation: identity verified plus an optional note capped at the frozen identity-note limit and carrying the UI-SPEC's do-not-enter-personal-data warning directly under the field; scope clarified; known dispute or litigation, unchecked by default, with a note that checking it stops nothing and simply carries forward to the lawyer.

`apps/web/src/ui/intake/expense-line-repeater.tsx` — section 3, a repeater of rows and never a grid; a grid invites paste-bombing and hides validation. Each row: a grouped category select over the closed 21-code taxonomy (staff time, materials and delivery, third-party charges, other), a description field capped at the frozen description limit, quantity, a unit select constrained by the chosen category, rate per unit, and a read-only computed amount rendered through `formatMinor`. Staff grade appears only for staff-time categories; the invoiced flag, vendor and evidence-reference fields appear only for third-party categories. Each row carries duplicate and delete controls. On category selection, render that category's hint from the view model. At zero rows render the UI-SPEC's empty-state heading and body. The line-count badge is singular or plural by count, including at one.

Field naming is load-bearing: no `name` or `id` attribute on any input, select or textarea in this screen may match `PERSONAL_DATA_DENY_LIST`. There is no field for the requestor anywhere, and the evidence reference is a pointer into the document system, never a document — there is no upload control in this application at all.

Add a clearly-labelled control that fills the repeater with the PRD §14 reference example's six rows. It populates form inputs only and computes nothing: every figure still comes from the engine after submit. Label it as filling the example rows so a viewer cannot read it as producing a result. Without it a live presenter types thirty-six fields on stage.

`apps/web/src/ui/intake/claim-footer.tsx` — the sticky footer: the running claimed total through `formatMinor` and the UI-SPEC's claim-not-the-fee sentence verbatim. Then the submit control, disabled until there is at least one line, every required field is valid and all three attestations have been addressed, with the specific unmet condition rendered beside it — a disabled button with no visible reason is a dead end.

`apps/web/src/ui/intake/intake-form.tsx` — the client component holding form state and composing the four pieces. On submit it posts the matter, then each line, then the submit route, and navigates to the confirmation page. All four of these components import nothing from `apps/web/src/server`; the pack view arrives as props.

`apps/web/app/(hr)/matters/[id]/submitted/page.tsx` — the confirmation: matter reference, and PRD §10.2's closing sentence verbatim about not seeing a figure before sign-off. That sentence is the whole point of the screen; without it HR reads the silence as a bug and starts asking Legal for the draft.

`apps/web/src/server/data/matters.ts` — add `replaceExpenseLine` and `deleteExpenseLine`, both role-checked and both refusing unless the matter is still DRAFT, and extend `apps/web/app/api/matters/[id]/lines/route.ts` with the matching `PUT` and `DELETE` handlers in the same thin shape as the existing `POST`.

`tests/routes/intake.test.ts` — route-level tests tagged `INTAKE`: a line edited after submit is refused with a conflict status and the stored line is unchanged; a line whose claimed amount disagrees with quantity times rate is rejected with 400 by the frozen schema rather than stored; a matter whose currency does not match its jurisdiction's designated currency is rejected with 400.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HR keyboard → free-text fields | The one place a person could type a requestor's name into this system; the architecture's job is to make that field nonexistent, not merely discouraged |
| client form state → line-creation route | Client-side validation is user experience; the frozen schema at the route is the enforcement point |
| rule pack content → intake hint text | Pack-authored strings are rendered to HR and shape what HR believes the rules are |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.1-08 | Information Disclosure | intake form fields | high | mitigate | No requestor field exists in any shape; the identity note is capped at the frozen limit and carries the do-not-enter warning; the rendered form is scanned against `PERSONAL_DATA_DENY_LIST` by a boundary test that now asserts a minimum scanned-field count so it cannot pass vacuously. |
| T-03.1-09 | Tampering | client-side line validation | medium | mitigate | Every line is re-parsed with the frozen `ExpenseLineSchema` inside the data layer, including the claimed-amount invariant, so a crafted request that bypasses the form is refused with 400 rather than stored. Asserted by a route test. |
| T-03.1-10 | Tampering | line edits after submit | medium | mitigate | `replaceExpenseLine` and `deleteExpenseLine` refuse unless the matter is still DRAFT, and the route test asserts the stored line is unchanged after the refusal — not merely that a status code came back. |
| T-03.1-11 | Spoofing | pack-authored hint text | low | mitigate | Hints render the pack's own `basis` string, which pack validation already scans for banned legal-conclusion words; no component may substitute a locally typed sentence, and the hint test asserts the rendered text equals the supplied prop. |
| T-03.1-12 | Tampering | free-text rendering | low | mitigate | All free text renders as JSX text nodes, so React escapes it; no raw-HTML rendering API is used anywhere in this plan. |
| T-03.1-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package. The phase's only new dependency was audited and human-verified in Plan 01 Task 0. |
</threat_model>
