# Phase 03.1: Code Review Report

**Reviewed:** 2026-09-18T00:00:00Z
**Depth:** standard
**Files Reviewed:** 61
**Status:** issues_found

## Summary

Reviewed the Phase 03.1 in-memory demo slice: the intake screen, the legal review screen, the
HR result/info-request screens, the route handlers, the data-access layer, the two in-memory
repositories, and the shared domain modules. The architectural invariants the task asked me to
verify actually hold: `apps/web/src/ui/**` never imports `apps/web/src/server/**` (confirmed by
both the dependency-cruiser rule and a direct grep), the repository interface stays free of any
concrete store import, every mutation goes through a Route Handler that calls a Data-Access-Layer
`requireRole()` first, money stays integer `Minor` throughout the paths reviewed, no rendered form
field name matches the personal-data deny list, no engine/pack-authored UI text carries a banned
legal-conclusion word, and `SIGNED_OFF` assessments cannot be re-mutated (the state guard in
`requireAssessmentInLegalReview` refuses every write once the matter has left `LEGAL_REVIEW`). The
deliberate pack-status coercion is correctly isolated to `coercePackForDemoEngine()`, and every UI
surface I checked (status strip, pack rail, intake pack view) reads the real, uncoerced
`loadDemoPack()` result.

Within that sound architecture, however, I found one demo-breaking navigation bug and several
real robustness/UX gaps that should be fixed before this is used in front of a stakeholder or
built on further.

## Critical Issues

### CR-01: The demo's own "Open an assessment, as Legal" link is dead, and there is no other way to reach the legal review screen

**File:** `apps/web/app/page.tsx:27`
**Issue:** The landing page (the one page whose job is to route a first-time visitor) links to
`/legal/assessments`. No `page.tsx` exists at that path — only at
`apps/web/app/(legal)/assessments/[id]/page.tsx`, which requires a dynamic `id` segment. Clicking
this link 404s.

This isn't just a bad link: there is no other path to the legal review screen anywhere in the
built UI. `apps/web/app/(hr)/matters/[id]/submitted/page.tsx` (the confirmation screen shown
immediately after HR submits) shows only a static confirmation sentence — it never surfaces the
matter id, the assessment id, or a link to review it. `apps/web/src/ui/hr/info-request-panel.tsx`
likewise never links back to the review screen. The only way to discover an assessment id today is
to read it out of a raw HTTP response (e.g. via browser devtools) — `tests/routes/walkthrough.test.ts`
does exactly this (`const assessment = (await submitRoute(...)).json()`), which is fine for a
test but not for the presenter's script this phase's own `docs/DEMO-WALKTHROUGH.md` describes.
Step 5 of that walkthrough ("Switch to the legal identity") has no route to actually click
through to.

This defeats the stated purpose of Phase 03.1 — "a demo-only slice of `apps/web` for a
stakeholder presentation" (README.md) — since the one entry point the app itself advertises does
not work.
**Fix:** Either link `apps/web/app/page.tsx`'s legal entry point directly at a real assessment
(acceptable for a single-pack demo, since there's effectively one matter/assessment moving through
the pipeline at a time), or add a minimal `/legal/assessments` listing page backed by
`memoryAssessmentRepository`/`memoryMatterRepository` that lists matters currently in
`LEGAL_REVIEW`/`INFO_REQUEST` with a link to each `[id]`. At minimum, surface the assessment id (or
a working link) on the HR submitted-confirmation page so the presenter has something to copy or
click.

## Warnings

### WR-01: Ask-HR / `INFO_REQUEST` resubmit is a no-op — HR has no way to actually change anything before resubmitting

**File:** `apps/web/src/server/data/matters.ts:120-178`, `apps/web/src/server/data/matters.ts:236-264`, `apps/web/app/(hr)/matters/[id]/page.tsx:32-46`
**Issue:** `resubmitAfterInfoRequest`'s own module comment says it "re-runs `assessMatter()` over
the CURRENT lines" — implying HR is expected to have changed something in response to the
lawyer's query. But `addExpenseLine`, `replaceExpenseLine` and `deleteExpenseLine` all refuse
unless `matter.status === "DRAFT"` (`ConflictError`), and the matter is `INFO_REQUEST`, not
`DRAFT`, for the entire duration this branch exists. The HR result page's `INFO_REQUEST` branch
(`apps/web/app/(hr)/matters/[id]/page.tsx:32-46`) renders only `InfoRequestPanel`, which shows the
lawyer's queries and a "Re-submit to Legal" button — there is no line-editing UI at all in this
state, and the API refuses edits even if one existed. In practice, clicking "Re-submit to Legal"
always recomputes an assessment byte-for-byte identical to the one Legal already reviewed and
asked a question about.
**Fix:** Either allow `addExpenseLine`/`replaceExpenseLine`/`deleteExpenseLine` while
`matter.status === "INFO_REQUEST"` (in addition to `DRAFT`) and give the HR result page a line-editing
view in that branch, or — if this is intentionally deferred to Phase 4/6 as the `InfoRequest` type's
own module note suggests — say so explicitly in the panel's copy (e.g. "line editing isn't wired
yet in this demo; resubmitting simply re-runs the same computation") so the control doesn't imply a
capability that isn't there.

### WR-02: The legal review page doesn't reflect matter status — a signed-off or info-requested assessment still renders live, actionable controls

**File:** `apps/web/src/server/data/assessments.ts:40-49` (`getAssessmentForLegalReview`), `apps/web/app/(legal)/assessments/[id]/page.tsx:52-79`
**Issue:** Unlike `getHrMatterStatus`, which explicitly branches on the matter's status,
`getAssessmentForLegalReview` performs no state check at all — it returns the assessment for any
matter status. The review page derives `pendingCount` purely from line dispositions, so:
- After sign-off, every line is already dispositioned, so `pendingCount === 0` and the
  `SignOffPanel` renders again with a live "Sign off and release to HR" button. Clicking it calls
  `POST /api/assessments/{id}/signoff`, which `requireAssessmentInLegalReview` correctly refuses
  with 409 — so the write is safe — but the screen itself gives no indication the matter was
  already signed off; the lawyer sees what looks like a normal, actionable review screen.
- While a matter is `INFO_REQUEST` (one line still `PENDING` from the Ask-HR question, the rest
  already dispositioned), the review screen still renders `DispositionControls` for the pending
  line, and a submit again 409s at the API layer with no state-aware messaging on the page itself.
**Fix:** Have the legal review page read the matter's status (already fetched via
`memoryMatterRepository.getMatter`) and render a distinct, non-actionable "already signed off, by
X on Y" or "awaiting HR's response to your question" view instead of the live review UI, the same
way `apps/web/app/(hr)/matters/[id]/page.tsx` already branches on `matter.status`.

### WR-03: Several data-layer mutation functions trust the request body's shape with no runtime validation, turning a malformed request into a 500 instead of a 400

**File:** `apps/web/src/server/data/assessments.ts` (e.g. `assertSufficientReason` at line 78-87, `bulkAcceptLines` at line 239-270, `signOff` at line 297-375, `askHr` at line 390-420)
**Issue:** `createMatter`/`addExpenseLine` (`apps/web/src/server/data/matters.ts`) validate their
input with `MatterSchema.parse`/`ExpenseLineSchema.parse` before touching it. `dispositionLine`,
`bulkAcceptLines`, `signOff` and `askHr` (`apps/web/src/server/data/assessments.ts`) do not — their
`DispositionLineInput`/`BulkAcceptInput`/`SignOffInput`/`AskHrInput` types are plain TypeScript
interfaces with no zod counterpart, and the route handlers cast the parsed JSON body directly
(`(await request.json()) as BulkAcceptInput`) with no runtime check. Concretely reachable crashes:
- `POST /api/assessments/{id}/bulk-accept` with a body that omits `reason` — `assertSufficientReason(undefined)` → `countNonWhitespaceChars(undefined)` calls `.replace()` on `undefined` → uncaught `TypeError`.
- `POST /api/matters/{id}/info-request` with a body that omits `query` — same crash via `assertSufficientReason`.
- `POST /api/assessments/{id}/signoff` with a body that omits `acknowledgedFlags` — the `for (const id of input.acknowledgedFlags)` loop at `assessments.ts:322` throws `TypeError: input.acknowledgedFlags is not iterable`; a body that omits `qualification` throws at `input.qualification.trim()`.

`errorToResponse` (`apps/web/src/server/errors.ts:58-67`) only special-cases `ZodError` and the
four typed application errors — a bare `TypeError` falls through to its generic `instanceof Error`
branch and is reported as a 500 with the raw JS error message, rather than a clean, typed 400.
**Fix:** Give `DispositionLineInput`/`BulkAcceptInput`/`SignOffInput`/`AskHrInput` matching zod
schemas (even minimal ones — `z.object({ reason: z.string(), ... })`) and `.parse()` the body in
each route handler or at the top of each data-layer function, the same way `matters.ts` already
does. This also closes the gap consistently for every one of these four entry points at once.

### WR-04: `addExpenseLine`'s `seq` derivation can produce duplicate line numbers after a delete

**File:** `apps/web/src/server/data/matters.ts:80-114` (`addExpenseLine`, `seq: existingLines.length`)
**Issue:** `seq` is assigned as `existingLines.length` — the count of lines currently on the
matter, not `max(existing seq) + 1`. `deleteExpenseLine` and `addExpenseLine` are both permitted
only while `matter.status === "DRAFT"`, so both are reachable in the same window through the public
`POST`/`DELETE /api/matters/{id}/lines` routes (wired and tested per
`apps/web/app/api/matters/[id]/lines/route.ts`, independent of the fact that the currently-built
intake UI's own delete button only mutates local React state and never calls the route). Sequence:
add three lines (seq 0, 1, 2) → delete the line with seq 1 (two lines remain: seq 0, seq 2) → add a
new line → `existingLines.length` is now 2, so the new line is also assigned `seq: 2`, colliding
with the surviving line. `listExpenseLines` sorts by `seq` (`matter-repository.ts:39`), and
`line-card.tsx` renders `Line {seq}` directly — two different lines would display as "Line 2" on
the review screen with no stable way to tell them apart.
**Fix:** Derive `seq` from the existing lines' own values, e.g.
`Math.max(-1, ...existingLines.map((line) => line.seq)) + 1`, rather than from the array length.

### WR-05: The capability statement's AI-drafting bullet is not true for this build

**File:** `apps/web/src/ui/capability/capability-statement.tsx:99-105`
**Issue:** The first-use capability statement — the one screen every user sees before touching the
tool — states: "Parts of the output are drafted by an AI language model. Those parts are labelled.
They may be wrong in wording even where the figures are right." Phase 03.1 has no LLM anywhere in
its pipeline (`packages/agent` is explicitly "last, not yet built" per `README.md`, and
`apps/web/src/ui/review/line-card.tsx`'s own module note confirms "there is no LLM anywhere in this
phase, so no text on this screen was generated that way"). No output in this build carries any such
label. This is the one piece of UI copy in the whole reviewed surface that makes a claim about the
system's actual capabilities that is not true today, in a codebase whose other disclosure copy
(the demo banner, the pack-status disclosure, the DEMO-WALKTHROUGH's own "the demo tells the
truth" framing) is otherwise scrupulous about not overstating what's built.
**Fix:** Either drop this bullet from the Phase 03.1 build (it's one of Annex A's six bullets, not
one of the frozen PRD non-negotiables), or add the same kind of explicit "not in this demo yet"
caveat the pack-status cell and demo banner already use elsewhere, so a stakeholder reading this
screen isn't told the demo does something it doesn't.
