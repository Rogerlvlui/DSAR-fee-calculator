# Phase 03.1 — Security

> Per-phase security contract: threat register, accepted risks, and audit trail.

---

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| browser → Route Handler | Untrusted JSON body and an untrusted role cookie cross here; everything past it is treated as validated only because it was parsed with a frozen schema | Matter/expense-line/disposition input, role cookie |
| Route Handler → Data Access Layer | The only place role authorisation is decided; a caller that skips it reaches the store unauthorised | `DemoActor`, request payloads |
| committed rule-pack JSON → engine input | The coerced in-memory copy lives here; if the coercion leaked into what the UI reports, the demo would misstate the pack's real standing | Rule pack content, `status` override |
| repository interface → store implementation | The swap seam Phase 3.2 depends on; an import across it in the wrong direction silently ends the swappability | `Matter`/`Assessment` domain types |
| assessment line verdict → permitted actions | The engine's verdict constrains what a lawyer may do to a line; a client offering the wrong control must still be refused | Disposition amount, reason |
| legal review → signed off | The transition after which a figure becomes visible outside the legal side | Attestation, six-condition gate |
| assessment record → HR-facing view | Privileged lawyer reasoning must not cross this boundary | `ResultViewLine` (structurally has no reason field) |
| rule pack notice template → requestor-facing draft | The only sanctioned source of requestor-facing wording is counsel's own authored template | Notice draft text |
| the build's self-description → a stakeholder's belief | The demo's claims about itself are the surface with the largest audience and the least functional-test coverage | Capability statement, status strip, watermark |
