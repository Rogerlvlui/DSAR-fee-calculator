  <files>packages/schemas/src/personal-data-pattern.ts, packages/schemas/src/personal-data-pattern.test.ts</files>
  <read_first>
    - docs/PRD-dsar-fee-agent.md §12.1 — "a lightweight pattern check (long digit strings, ID-number-shaped tokens, email addresses) warns before submit. Warn, do not block; false positives on invoice numbers would be maddening."
    - packages/schemas/src/constants.ts — this module's own header comment convention (exported once, imported everywhere else) — this task's new file follows the same convention
    - .planning/phases/05-hr-intake-and-disclosure-shell/05-RESEARCH.md, Architecture Patterns Pattern 4 and Assumption A3 — the three named pattern shapes and the explicit false-positive risk on `evidenceRef`/`vendorName`, which this function is never wired to
  </read_first>
  <behavior>
    - Test: an email address anywhere in the string is detected, with a reason mentioning an email address.
    - Test: a Singapore NRIC/FIN-shaped token (one letter, seven digits, one letter — e.g. "S1234567A") is detected, with a reason distinguishing it from the email case.
    - Test: a run of seven or more consecutive digits with no letter-digit-letter shape around it is detected as a long digit run.
    - Test: an ordinary sentence with no matching pattern returns `matched: false` and a `null` reason.
    - Test: a plausible invoice-number-shaped string like "INV-88421" (five digits, hyphen-prefixed, no NRIC-shaped letter bracket) does NOT match the digit-run pattern — the false positive PRD §12.1 explicitly worries about.
    - Test: the function never throws for any string input, including the empty string.
  </behavior>
  <action>
Create `packages/schemas/src/personal-data-pattern.ts` following `constants.ts`'s own single-source-of-truth convention: a module comment naming this as PRD §12.1's warn-never-block check, exported once, used by the intake screen now and Phase 6's `lawyerReason` review-screen wiring later (do not wire `lawyerReason` here — that is explicitly Phase 6's job, per this phase's own ROADMAP closing note).

Export `interface PersonalDataPatternMatch { matched: boolean; reason: string | null }` and `function detectLikelyPersonalData(value: string): PersonalDataPatternMatch`. Three ordered checks, first match wins: an email-shaped substring (`/[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}/i`), a Singapore NRIC/FIN-shaped token (`/\b[A-Za-z]\d{7}[A-Za-z]\b/`), and a run of seven or more consecutive digits (`/\d{7,}/`) with no letter immediately adjacent on either side (so the NRIC-shaped check above, which is more specific, does not also fire the generic digit-run check redundantly — check order matters here: test the NRIC shape before the bare digit run). Return `{ matched: false, reason: null }` when none match.

This function is deliberately narrow and hand-authored, not backed by a PII-detection package — the three shapes above are the entire scope PRD §12.1 asks for, and a broader package would need its own Package Legitimacy Gate for no benefit this phase needs. It must never throw and never truncate its input; it is a pure, total function over any string.
  </action>
