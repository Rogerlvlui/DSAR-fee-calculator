  <behavior>
    - Test: `writeDraftToStorage(key, value)` against a real (jsdom) `localStorage` returns `true` and stores the JSON-serialised value.
    - Test: `writeDraftToStorage(key, value, storage)` against a hand-built storage object whose `setItem` throws returns `false` without throwing itself.
    - Test: mounting a component that calls `useDraftAutosave(key, value)` under `vi.useFakeTimers()`, before any time advances, reports `status: "idle"` and writes nothing to storage yet.
    - Test: advancing fake timers by 10 seconds causes exactly one write to storage carrying the current `value`, and the hook's reported status becomes `"saved"` with a non-null `savedAt`.
    - Test: advancing fake timers by a further 10 seconds with a CHANGED `value` (proving no stale-closure bug) writes the NEW value, not the one captured at mount.
    - Test: when the underlying storage write throws, the hook's reported status becomes `"error"` rather than `"saved"`, and no exception escapes the component tree.
    - Test: unmounting the component before the next tick clears the interval — verified by advancing fake timers again after unmount and asserting no further write occurs.
  </behavior>
  <action>
Export `writeDraftToStorage(key: string, value: unknown, storage: Pick<Storage, "setItem"> = window.localStorage): boolean` — `JSON.stringify(value)` then `storage.setItem(key, ...)` inside a try/catch, returning `false` on any thrown error (a full `localStorage`, a disabled-storage browser setting, or a hand-built failing mock in tests) rather than letting the exception propagate. This is the one fully synchronous, dependency-free piece, and it is tested directly with no React involved for the two storage-behavior cases.

Export `type AutosaveStatus = "idle" | "saving" | "saved" | "error"` and `interface AutosaveState { status: AutosaveStatus; savedAt: number | null }`, and the hook itself: `useDraftAutosave(key: string, value: unknown, intervalMs: number = 10_000): AutosaveState`. Hold `value` in a `useRef` updated on every render (so the interval callback always reads the LATEST value, never a value captured once at mount — the stale-closure bug this task's own test list explicitly checks for). On mount, `setInterval` an async callback that: sets status to `"saving"`, awaits a `Promise.resolve()` (a deliberate microtask boundary — React's automatic batching would otherwise collapse a synchronous `"saving"` update and the immediately-following `"saved"`/`"error"` update into a single render, making the "saving" state genuinely untestable and, per the UI-SPEC's own requirement above, it must exist), then calls `writeDraftToStorage(key, valueRef.current)` and sets status to `"saved"` (with `savedAt: Date.now()`) or `"error"` accordingly. Clear the interval on unmount.

Mount the test component for the timer-driven cases using `react-dom/client`'s `createRoot` inside `act` (imported from `"react"`, not `react-dom/test-utils` — React 19's own current location) under the `web` project's real jsdom environment; this needs no new dependency, since `createRoot` and `act` both ship with `react`/`react-dom`, already dependencies of this app.
  </action>
